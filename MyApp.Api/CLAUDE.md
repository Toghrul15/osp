# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Backend for an Online Shopping Platform: catalog, cart, orders with status tracking, addresses, admin panel, search/filtering, reviews, coupons. ASP.NET Core Web API on **.NET 10**, EF Core with **SQL Server** (LocalDB in development), ASP.NET Core Identity with JWT bearer auth.

The solution lives one level up from this folder: `final-project/MyApp.slnx`, with sibling projects `MyApp.Core`, `MyApp.DAL`, `MyApp.BLL` and this `MyApp.Api`. The full roadmap (data model, checkout flow, order status rules, phases 1–6) is in the plan this project was started from; Phase 1 (foundation, database, auth) is done.

## Commands

Run from this directory (`MyApp.Api`):

- Build everything: `dotnet build ../MyApp.slnx`
- Run: `dotnet run --launch-profile http` (http://localhost:5127) or `--launch-profile https` (https://localhost:7023)
- Add a migration: `dotnet ef migrations add <Name> --project ../MyApp.DAL --startup-project . --output-dir Migrations`
- Apply migrations: `dotnet ef database update --project ../MyApp.DAL --startup-project .`
- Tests: none yet. Once a test project exists: `dotnet test --filter "FullyQualifiedName~ClassName.MethodName"`

The `dotnet ef` commands need `ASPNETCORE_ENVIRONMENT=Development` (in PowerShell: `$env:ASPNETCORE_ENVIRONMENT='Development'`), because the connection string and JWT secret live only in `appsettings.Development.json`. That file is git-ignored; on a fresh clone, copy `appsettings.Development.example.json` to it and fill in the secret and admin password. The app does **not** apply migrations on startup; run `database update` first or startup seeding fails.

`MyApp.Api.http` has ready-made requests (register, login, `/me` using the login token).

API docs (Development only): Swagger UI at http://localhost:5127/swagger, raw OpenAPI at `/openapi/v1.json`. The document is generated by the built-in `Microsoft.AspNetCore.OpenApi`; `Swashbuckle.AspNetCore.SwaggerUI` only provides the UI. `OpenApi/ApiInfoTransformer` adds the title and the JWT `Bearer` scheme, and `OpenApi/AuthorizeOperationTransformer` adds the lock and a "Requires role" note to every `[Authorize]` endpoint. Descriptions come from `///` XML comments (enabled in Api and BLL). **Every new endpoint needs a `<summary>`, `<response>` lines and matching `[ProducesResponseType]` attributes.** Enums are serialized as strings (`JsonStringEnumConverter`).

## Architecture (layered)

Dependencies go strictly downward: **Api → BLL → DAL → Core**.

- **MyApp.Core**: entities (`Entities/`), enums, `Constants/Roles` (`Admin`, `Vendor`, `Customer`). `AppUser : IdentityUser`. Entities derive from `BaseEntity` (int `Id`, `CreatedAt`, `UpdatedAt`). The timestamps are set automatically in `AppDbContext.SaveChanges*`; never set them by hand.
- **MyApp.DAL**:
  - `AppDbContext : IdentityDbContext<AppUser>`, with one `IEntityTypeConfiguration<T>` per entity in `Data/Configurations/`. Relationships, indexes, check constraints and delete behaviour go there, not in attributes.
  - A global convention makes every `decimal` `decimal(18,2)`.
  - Generic `IRepository<T>` (exposes `Query()`, no tracking by default).
  - `AddDal()` registers the DbContext and Identity (`AddIdentityCore`, no cookies).
  - `Seed/DbSeeder` creates the roles plus the admin account from `SeedAdmin:*` config.
- **MyApp.BLL**:
  - DTOs, services (interface and implementation in the same file), `JwtOptions`, `AppClaimTypes`.
  - Exceptions in `Exceptions/AppException.cs` (`BadRequest`/`Unauthorized`/`Forbidden`/`NotFound`/`Conflict`). Services throw these to signal errors.
  - `AddBll()` calls `AddDal()` and reads `ConnectionStrings:DefaultConnection`.
- **MyApp.Api**:
  - Thin controllers that call BLL services and never use `AppDbContext` directly.
  - `Middleware/AppExceptionHandler` converts `AppException` into a ProblemDetails response with its status code; anything else becomes a 500.
  - `Services/CurrentUserService` implements the BLL's `ICurrentUserService` from the JWT claims.
  - `Program.cs` is the composition root and is intentionally kept free of comments.

## Conventions and gotchas

- JWT claims use short names (`sub`, `email`, `name`, `role`; see `AppClaimTypes`). `MapInboundClaims = false`, so read the user id with `AppClaimTypes.UserId`, not `ClaimTypes.NameIdentifier`. `[Authorize(Roles = Roles.Admin)]` works because `RoleClaimType = "role"`.
- Enums (`OrderStatus`, `PaymentStatus`, `CouponType`) are stored as strings.
- `Order.ShippingAddress` is an EF complex type (columns `ShippingAddress_*`): a copy of the address at order time. `OrderItem` likewise stores `ProductName` and `UnitPrice`, so orders never depend on the current product data.
- `Product.RowVersion` is a concurrency token. Checkout must catch `DbUpdateConcurrencyException` when decreasing stock and return 409.
- `Product.IsDeleted` is a soft-delete flag with **no** global query filter. Filter it explicitly in catalog queries.
- Delete behaviour: links to orders, products, categories and vendors use Restrict, so history is never cascade-deleted. Avoid adding cascades that create multiple cascade paths, which SQL Server rejects.
- `AverageRating`/`ReviewCount` on `Product` are stored totals. Recalculate them whenever reviews change.
- Request validation currently uses DataAnnotations on DTOs (`[ApiController]` returns 400 automatically).
- Catalog (F1): categories/tags are Admin-only writes; products are written by `Admin,Vendor`, and `ProductService.EnsureCanManage` limits vendors to their own products. Slugs come from `BLL/Common/SlugHelper` and must be unique (409). Product images are saved by `Api/Services/LocalFileStorage` (`IFileStorage`) under `wwwroot/uploads/products` and served by `UseStaticFiles`. Paged lists return `BLL/Common/PagedResult<T>`.
- Search (F6): `GET /api/products` binds `ProductQuery` (search, categoryId incl. subcategories, tagId, minPrice/maxPrice, minRating, inStock, sort = `ProductSort` enum bound by name, page/pageSize). Filters are applied in `ProductService.GetPagedAsync`; every sort has an `Id` tie-breaker so paging is stable.
- Cart (F2): `api/cart`, any authenticated user, always for the current user (`ICurrentUserService.UserId`). Items are addressed by `productId`. The cart is created lazily on the first add. Prices are **not** stored on `CartItem`; `CartService.GetAsync` uses the product's current price, flags items that are inactive, deleted, out of stock or over stock (`IsAvailable`, `Issue`), leaves unavailable items out of the subtotal, and sets `Summary.CanCheckout` only when there are no issues. Checkout (F3) must re-check stock itself. Limits are in `CartLimits` (99 per item, 50 distinct items).
- Transactions: use `MyApp.DAL/IUnitOfWork` (`BeginTransactionAsync`, `SaveChangesAsync`); all repositories share the same scoped `AppDbContext`, so one `SaveChangesAsync` saves everything.
- Addresses (F4, part 1): `api/account/addresses`, own addresses only (others → 404). A filtered unique index allows **one default per user**, so `AddressService` always clears the old default and saves *before* setting the new one, inside a transaction. `GetShippingAddressAsync` returns the copy stored on an order.
- Orders (F3): checkout `POST api/orders` (cart + `addressId`) re-checks stock, copies product name/price and the address, decreases stock, empties the cart and adds the first `OrderStatusHistory` row in one transaction; `DbUpdateException` → 409. Allowed status moves live in `OrderService.Transitions` (Pending → Processing/Cancelled, Processing → Shipped/Cancelled, Shipped → Delivered). Cancelling restores stock; Delivered sets `PaymentStatus.Paid` (cash on delivery). Customers cancel only while Pending; admins change status via `api/admin/orders`. `Order.Status` is a concurrency token, so simultaneous status changes give 409. Shipping cost is 0.
- Coupons (F8): admin CRUD at `api/admin/coupons`; customers check a code with `POST api/coupons/preview` and use it via `couponCode` on checkout. Codes are stored upper case. All rules live in `CouponService.GetUsableCouponAsync` (active, StartsAt/ExpiresAt in UTC, usage limit, MinOrderAmount); the discount is `CouponService.CalculateDiscount` (percentage rounded to 2 decimals, never more than the subtotal). A use is taken with an atomic `ExecuteUpdate` (`UsedCount + 1 WHERE UsedCount < UsageLimit`) inside the checkout transaction and given back on cancel; these `ExecuteUpdate` calls bypass `SaveChanges`, so they set `UpdatedAt` themselves (the one exception to the timestamp rule). Used coupons can't be deleted (409), only deactivated. No per-customer limit.
